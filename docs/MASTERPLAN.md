## 1. Product summary

A free, fast, ad-free website where anyone can learn and practice typing Bangla on a PC keyboard, with structured lessons, speed tests, and honest progress tracking. It works in the browser with no install, no sign-up, and no data leaving the user's device.

**One-line pitch:** *Monkeytype's speed and polish, plus Keybr-style adaptive practice, built for Bangla.*

### Why it should exist
Millions of Bangla speakers type in Bangla for school, government forms, jobs, and business, yet most learn by trial and error. The tools that exist are either old desktop programs, ad-heavy pages, or English-first trainers that do not handle Bangla's conjuncts and vowel signs. Bangla typing is also a real job skill (data entry, office roles, typing tests in recruitment). A modern, free, open-source trainer fills a real gap. (Owner should confirm the gap by a quick search of existing Bangla typing tutors before launch — see Section 18.)

### Goals
1. A beginner can learn a layout from zero and reach comfortable speed using only this site.
2. Typing a Bangla word is judged correctly even though Bangla text has combining characters and multiple valid keystroke paths.
3. Loads almost instantly, works offline after first visit, scores 95+ on Lighthouse (mobile-emulated performance is still checked even though the app is PC-focused).
4. Ranks for Bangla typing search queries without paid promotion.
5. Zero running cost. Static hosting only.

### Non-goals (do NOT build in v1)
Accounts/login, leaderboards, multiplayer, payments, ads, AI-generated lessons at runtime, mobile touch keyboard training, voice typing, a full word processor, a browser extension, server-side anything.

## 3. Key product decisions

1. **Two input modes.**
   - **Built-in mode (default):** the app itself converts keystrokes into Bangla. No software install needed. MVP supports **Avro Phonetic** (type Roman letters, get Bangla), which is the most popular method among general users.
   - **System keyboard mode:** the user already has a Bangla keyboard installed (Avro Keyboard, OS layout, UniBijoy, Probhat…). The app just reads the Unicode text that their keyboard produces and compares it to the target. This instantly supports every layout for practice, with zero engine work, but cannot show which physical key to press.
2. **Fixed layouts come after MVP.** v1.1 adds the national layout (BDS 1738) and Probhat with on-screen key hints. Do not ship a layout whose license is unclear (see Section 17, risk on Bijoy).
3. **Unicode only.** Never use ANSI/legacy Bijoy font encodings.
4. **Judge output, not keystrokes.** A word is correct if the final Unicode string matches the target after normalization, no matter which keystrokes produced it.
5. **No database.** Progress and settings live in `localStorage`, with JSON export/import so users can move devices. No analytics that sets cookies.
6. **Bangla-first UI**, with an English toggle. Default language `bn`.
7. **Static site, prerendered pages** for SEO; the typing area is a small interactive island.

## 7. Typing engine and logic (the hard part — read carefully)

### 7.1 Architecture of the core
Keep the engine framework-free (plain TypeScript modules) so it is unit-testable and reusable.

```
src/engine/
  unicode.ts        # normalization, cluster splitting, constants
  compare.ts        # target vs typed comparison → per-cluster states
  metrics.ts        # WPM, accuracy, per-character stats
  session.ts        # run state machine (idle → running → finished)
  input/
    types.ts        # InputEngine interface
    system.ts       # System keyboard mode
    phonetic.ts     # Avro Phonetic engine (built-in)
    phonetic-rules.json
  text/
    provider.ts     # picks/loads target text
```

`InputEngine` interface (guideline):
```ts
interface InputEngine {
  id: 'system' | 'avro-phonetic' | string;
  // feed a keyboard event, get the new committed + composing output
  handle(state: EngineState, ev: KeyInput): EngineState;
  reset(): EngineState;
}
type EngineState = { committed: string; composing: string; buffer: string };
```

### 7.2 Session state machine
`idle` → (first valid key) → `running` → (target fully typed or timer ends) → `finished`. Timer starts on the first keystroke, not on page load. Restart via `Tab+Enter` or button. Pausing is not supported in tests (it breaks fairness); lessons may allow it.

### 7.3 Bangla text pitfalls the engine MUST handle
Write tests for every one of these.

1. **Normalization.** Some Bengali letters (ড়, ঢ়, য়) can be one precomposed code point or a base letter plus nukta (U+09BC). Normalize **both** target and typed strings to the same form (NFC) before comparing. Test: precomposed vs decomposed inputs must compare equal.
2. **Grapheme clusters.** A visual "character" can be several code points: consonant + hasanta (্) + consonant (conjunct), plus vowel signs (া ি ী ু ূ ৃ ে ৈ ো ৌ), chandrabindu (ঁ), anusvara (ং), visarga (ঃ). Split the target into clusters and compare/color per cluster. **Do not rely only on `Intl.Segmenter`** — how it treats Indic conjuncts depends on the browser's Unicode/ICU version. Implement and test your own cluster splitter (defined below) and optionally use `Intl.Segmenter` as a cross-check in tests.
   - Cluster ≈ `[independent vowel | consonant(+nukta)] ( hasanta consonant(+nukta) )* [ZWJ/ZWNJ]? [vowel sign]* [chandrabindu|anusvara|visarga]*`.
3. **Zero-width joiners.** Forms like র‍্য (ra + ZWJ + hasanta + ya) use U+200D / U+200C. Preserve them in target text and treat them as part of the cluster; do not strip them.
4. **Khanda ta (ৎ, U+09CE)** is its own code point — do not confuse with ত + hasanta.
5. **Bengali digits** ০–৯ vs ASCII digits: the target text decides which appears; the engine's digit output must be configurable (Avro Phonetic outputs Bengali digits — verify against the reference).
6. **Multiple valid keystroke paths.** Different Roman spellings may yield the same Bangla (for example long/short vowel variants). Only the final Unicode matters.
7. **Backspace** in Built-in mode removes the last Roman keystroke and re-renders the composing text; in a committed word it removes the last committed cluster. Define this precisely and test it.
8. **Composing vs committed.** The Roman buffer is re-converted on every keystroke; while a word is being typed, its converted output may change (e.g. `k` → ক, then `kh` → খ). Color the current word tentatively; finalize on space/Enter.
9. **Do not break on OS IMEs.** In Built-in mode, ignore `compositionstart/update/end` events and warn the user (Section 5.2). Use `keydown` for letters and `beforeinput` for a fallback. Set `autocomplete="off" autocapitalize="off" spellcheck="false"` on the hidden input.
10. **Paste is blocked** during runs (except in Custom Text setup).

### 7.4 Comparison algorithm
Compare **word by word**, never by one global index across the whole text. A single early mistake (an extra or missing cluster) must not shift and mark every later character wrong.
1. Normalize the target once when a run is created; split it into words on spaces, and each word into clusters.
2. The user types the current word. Its typed output is normalized and split into clusters `U[0..m)`; the target word has clusters `T[0..n)`.
3. While the word is being typed: for `i < m`, state = `correct` if `U[i] === T[i]`, else `wrong`; for `i >= m`, `pending`; if `m > n`, the extra clusters are `extra`.
4. When the user commits the word (space/Enter), the word is final and is counted correct only if the whole normalized string equals the target word. Then move to the next word; a wrong word never affects the next one.
5. Optional setting "stop on error" (beginner lessons): the user must fix the current word before it commits.
6. Extra spaces or a missing space are handled at the word level (an empty or merged word counts as one wrong word); write tests for these.

### 7.5 Metrics (define once, test thoroughly, show definitions on the results page and the FAQ)
- **Committed word:** a word the user finished with space/Enter. Only committed words are scored (the last word is committed when the run ends).
- **Correct word:** a committed word whose normalized text equals the target word.
- **WPM** = correct words ÷ elapsed minutes. **KPM** = total keystrokes ÷ elapsed minutes (raw effort, shown as a secondary number).
- **Accuracy** = correct clusters ÷ total target clusters in committed words, as a percentage. Also track **corrected mistakes** (backspaced errors) separately so beginners can see that fixing errors is normal.
- **Elapsed time:** from the first keystroke to the last committed word (or the timer end for timed tests).
- **Error map:** per target cluster, count of times it was mistyped; this powers the "most missed" list and later adaptive drills.
- Write the exact formulas in `DECISIONS.md` and add tests with hand-calculated examples (for example: 10 target words, 8 correct, 60 seconds → 8 WPM).

### 7.6 Avro Phonetic engine (built-in mode)
- Data-driven: a rules file mapping Roman sequences to Bangla output, with longest-match-first scanning and context rules (for example how vowels behave after consonants, conjunct formation, reph, ya-phala, hasanta via `` ` ``, etc.).
- **Do not invent the rules.** Base the engine on the publicly documented Avro Phonetic behavior. Before copying any rules or code from an existing project, check its license and compatibility with MIT; if unclear, write the rule table from documentation yourself and log the source in `DECISIONS.md`. Every rule row gets a test.
- **Starter test cases** (confirm each against a reference implementation and a native speaker, then extend to 200+): `ami` → আমি; `amar` → আমার; `bangla` → বাংলা; `kaj` → কাজ; `bhalo` → ভালো; `ami banglay gan gai` → আমি বাংলায় গান গাই.
- Provide an on-page "cheat sheet" of the most common phonetic patterns (also useful as an SEO page).

### 7.7 System keyboard mode
The hidden input receives whatever Unicode the user's own keyboard software sends. Run the same normalization + cluster comparison. Detect obviously wrong input (Latin letters arriving when Bangla is expected) and show a hint: "Switch your keyboard to Bangla."

### 7.8 Fixed layouts (v1.1)
Map physical keys via `KeyboardEvent.code` (layout-independent) + Shift/AltGr to Bangla output per layout definition file (`layouts/national.json`, `layouts/probhat.json`). Handle vowel-sign ordering in logical Unicode order. Render an on-screen keyboard from the same JSON with finger colors and highlight the next key. Verify each layout's data against its official specification/source and record the license of that data.

### 7.9 Text selection logic
- Text sets have a difficulty tag: `easy` (common short words), `medium` (sentences), `hard` (conjunct-heavy words, numbers, punctuation).
- Random selection avoids repeating the last N texts. Lessons use fixed text.
- All text is validated at build time: only Bengali block characters + allowed punctuation/space; no stray Latin characters, no mixed encodings. A build script fails the build on invalid text.

## 8. Curriculum and content

### Lesson path (each lesson: intro → drill of ~30–60 seconds → pass at ≥ 90% accuracy)
1. Getting ready: posture, hand position, how Built-in mode works.
2. Common vowels and simple words (অ আ ই ঈ উ ঊ + very short words).
3. Common consonants, group 1 (ক খ গ ঘ ও…) and simple word building.
4. Common consonants, group 2 (চ ছ জ ঝ, ট ঠ ড ঢ, ত থ দ ধ ন…).
5. Consonants group 3 (প ফ ব ভ ম, য র ল শ ষ স হ, ড় ঢ় য়).
6. Vowel signs (kar): া ি ী ু ূ ৃ ে ৈ ো ৌ.
7. Chandrabindu, anusvara, visarga, khanda-ta.
8. Conjuncts (juktakkhor) part 1: very common ones.
9. Conjuncts part 2: harder ones and reph/ya-phala/ra-phala.
10. Numbers and punctuation (Bengali digits, দাঁড়ি ।, comma, quotes).
11. Full sentences, then paragraphs.
12. Real-world text: a formal application, a news-style paragraph, an email.

Exact key groups depend on the layout; for Avro Phonetic, teach by **sound patterns** rather than key positions.

### Content rules
- Prefer **original sentences** written for this project, reviewed by a native Bangla speaker. Store them as JSON/Markdown files in `content/`.
- Classic literature is allowed only when the author's copyright has clearly expired and you can cite the source; when in doubt, do not use it. Never scrape news sites or books.
- Every text item has: `id`, `text`, `difficulty`, `topic`, `source: original`, `reviewed: true/false`. Unreviewed text is not shipped to production.
- Avoid political, religious-controversy, or medical-advice content in practice text. Keep it neutral and everyday.
- Target library at launch: ~150 short texts, ~60 paragraphs, ~12 lessons.

Everything stays in the browser.

`localStorage` keys (versioned, all JSON):
- `tk:v1:settings` — `{ lang, theme, fontSize, inputMode, layout, difficulty, sound }`
- `tk:v1:runs` — array of `{ id, ts, mode, textId, wpm, kpm, accuracy, durationMs, errors:[{expected,typed}] }`, capped at the most recent 500.
- `tk:v1:lessons` — `{ [lessonId]: { bestAccuracy, bestWpm, completedAt } }`
- `tk:v1:errorMap` — `{ [cluster]: { missed, seen } }`

Rules:
- Wrap storage in a small module with schema versioning and migration; never assume keys exist; handle storage being unavailable or full (private mode) by falling back to in-memory and telling the user.
- **Export/Import:** download a single JSON file; import validates the schema and asks before overwriting.
- **Reset:** one button that clears all `tk:*` keys, with a confirmation.
- No personal data is collected, so no consent banner is needed. State this plainly on a Privacy page.

## 10. Technical architecture and stack

**Recommended stack (simple, fast, SEO-friendly)**
- **Astro** (static site generation) + **TypeScript**. Content pages are prerendered HTML; the typing UI is a small client-side island.
- Island UI: **Preact** or **Solid** (tiny) — or plain TypeScript if you prefer. Avoid heavy frameworks.
- Styling: **Tailwind CSS** with CSS-variable design tokens (Section 6), or hand-written CSS with the same tokens. Pick one and log it.
- Charts: hand-rolled SVG or one tiny library; no big chart packages.
- PWA: a service worker (for example via `@vite-pwa/astro`/Workbox) for offline caching of the app shell, fonts, and content.
- Tests: **Vitest** (unit), **Playwright** (a few end-to-end smoke tests), **axe** (accessibility checks), **Lighthouse CI** (performance/SEO budgets).
- Lint/format: ESLint + Prettier + TypeScript `strict`.
- Package manager: pnpm or npm (choose one).
- Hosting: **Cloudflare Pages** (or Vercel/Netlify/GitHub Pages) — free static hosting, automatic deploys from the repo.
- CI: GitHub Actions running lint, type-check, unit tests, build, Lighthouse CI on every PR.

**Folder structure (guideline)**
```
/
├─ docs/  MASTERPLAN.md  PROGRESS.md  DECISIONS.md  VERIFY.md
├─ content/  lessons/  texts/  guides/
├─ public/  fonts/  icons/  og/  robots.txt
├─ src/
│  ├─ engine/          (framework-free logic + tests)
│  ├─ components/      (UI islands)
│  ├─ layouts/  pages/ (Astro pages, bn + en)
│  ├─ i18n/            (bn.json, en.json)
│  ├─ styles/          (tokens.css, global.css)
│  └─ lib/             (storage, utils)
├─ scripts/            (validate-text, build-sitemap helpers, og image gen)
├─ tests/  e2e/
└─ package.json  astro.config.mjs  LICENSE  README.md
```

**Build-time checks (fail the build if violated):** invalid characters in content, missing translations, unreviewed content in production, missing SEO metadata on any page, bundle-size budget exceeded.

## 12. Performance, privacy, security

**Performance budget**
- Initial JS for the home page: aim for under ~60 KB gzipped (engine + island). Lazy-load charts and the progress page.
- Fonts: subset, WOFF2, preload one weight; measure font payload and keep it as small as practical.
- No render-blocking third-party scripts. Images are SVG/AVIF/WebP with dimensions set.
- Cache static assets long-term with content hashes; the service worker serves the offline shell.

**Privacy**
- No accounts, no cookies, no fingerprinting. Optional privacy-friendly, cookieless page-view analytics only (or none). State this on `/privacy`.
- Custom text and progress never leave the device.

**Security**
- Strict Content-Security-Policy via static-host headers (no inline scripts if avoidable), `X-Content-Type-Options`, `Referrer-Policy`.
- Import of progress JSON is schema-validated and never `eval`ed.
- Dependencies pinned, Dependabot on, minimal dependency count.

## 13. Testing and QA

- **Unit tests (must exist):** normalization equivalence, cluster splitting (with a table of tricky words), comparison states, metrics math, phonetic engine (200+ cases when done), backspace behavior, storage migration.
- **E2E smoke (Playwright):** open home → type a known sentence in System mode → see results; switch theme; export and re-import progress; offline reload works.

- **Cross-browser (desktop):** latest Chrome, Edge, Firefox, Safari. Test Bangla rendering (conjunct clipping) in each.

- **Content QA:** a native speaker checks all Bangla UI text, lessons, and texts; results tracked in `docs/VERIFY.md`.

## 16. Roadmap (phases with acceptance criteria)

**Phase 0 — Foundation (day 1)**
Save masterplan to `docs/MASTERPLAN.md`, create `PROGRESS.md`, `DECISIONS.md`, `VERIFY.md`, README, license; scaffold Astro + TypeScript; CI running lint/type-check/tests; deploy an empty page. *Done when:* a preview URL loads, CI is green, the attribution guard (hook + CI script + test) is in place, and `git shortlog -sne --all` shows only the owner.

**Phase 1 — Design system and shell**
Tokens (light/dark), fonts (self-hosted, subset), layout, header/nav, settings drawer, i18n (bn/en), theme switching. *Done when:* every shell page is responsive, passes axe, and the Bangla font renders correctly.

**Phase 2 — Engine core (System mode)**
`unicode.ts`, cluster splitter, normalization, comparison, metrics, session state machine, TypingArea island, results screen. *Done when:* unit tests cover Section 7.3 pitfalls; a user with Avro Keyboard installed can complete a run with correct scoring.

**Phase 3 — Built-in Avro Phonetic mode**
Rule table, engine, backspace, composing display, "OS keyboard on" warning, cheat sheet data. *Done when:* 200+ test cases pass and a native speaker signs off the first 100 in `VERIFY.md`.

**Phase 4 — Content and lessons**
Curriculum pages, lesson runner with pass criteria, text library, build-time content validator, custom text mode. *Done when:* 12 lessons and ~150 reviewed texts are in.

**Phase 5 — Progress and persistence**
Storage module with versioning, run history, error map, progress page, export/import/reset. *Done when:* data survives reloads, import/export round-trips, storage-unavailable path works.

**Phase 6 — SEO, PWA, performance**
Prerendered content pages, guides, sitemap, structured data, OG images, service worker, performance budget. *Done when:* Lighthouse ≥ 95 in all four categories on home and a lesson page.

**Phase 7 — QA and launch**
Cross-browser/OS pass, content sign-off, privacy page, README polish, release `v0.1.0`, submit to Search Console, share in communities. *Done when:* the Launch Checklist (Section 19) is fully ticked.

**Realistic time (one person + AI, part-time):** roughly 3–5 weeks to MVP. The phonetic engine and Bangla content review are the schedule risks, not the UI.

## 17. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Phonetic rules wrong or incomplete | Users learn wrong mappings | Data-driven rules, 200+ tests, native-speaker sign-off, publish rules openly for corrections |
| Bangla rendering/cluster bugs across browsers | Wrong coloring, clipped glyphs | Own cluster splitter, cross-browser tests, tricky-word table |
| OS keyboard conflicts with Built-in mode | Confusing garbage input | Detection + clear warning + System mode fallback |
| Layout licensing (Bijoy is proprietary/patented per press coverage) | Legal exposure | Ship Avro Phonetic first; add national layout (BDS 1738) and Probhat only after verifying the data source's license; do not call anything "Bijoy" without permission; support Bijoy users through System mode |
| Content copyright | Takedown | Original text only, or clearly expired-copyright sources with citations |
| Low adoption | Wasted effort | Validate early (Section 18); SEO pages and community sharing |
| Scope creep | Never ships | Non-goals list, phase gates, `DECISIONS.md` |
| AI tool leaves attribution/co-author trailers | Repo shows extra contributors | Sole-authorship rule in Section 0, automated hook + CI check, per-phase `git shortlog` verification |

## 18. Validation before investing heavily

1. **Gap check (1 hour):** search for existing Bangla typing tutors and note what they lack. Continue only if a clear gap remains (for example: no modern, ad-free, offline-capable tool that handles conjuncts and shows honest stats).
2. **Prototype test (weekend):** build only Phase 2 System-mode with 10 texts and share it with 10 people who type in Bangla. Ask: would you use it again? What annoyed you?
3. **Signal to continue:** at least several people return unprompted or ask for lessons; then build Phases 3–7.
